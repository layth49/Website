L.Λ.I.T.H.49

Logical Assistant for Intelligent Task Handling

My voice assistant for Windows. Say "Hey 49" and it's a real conversation: it hears you and answers in the same breath, and somewhere in there it works out whether to fire one of its 38 tools or just talk back. It keeps standing rules while I'm away, picks up whatever was pending after a reboot, and screens my phone calls when I arm it. Same C# core, two builds: cloud on the Gemini Live API, or fully local on faster-whisper, Kokoro, LM Studio and SearxNG.

How a turn works

[ WAKE → CONVERSE → ACT → SPEAK ]

It sits there listening for the wake word on-device. Once it hears it, the mic opens a live session and audio goes both ways for as long as you're talking. You don't press anything and you don't wait for a turn to finish. Every tool goes up as a function-calling schema, so mid-sentence it can pick tools, chain them together, or just answer you.

01
WAKE + GREET On-device Azure KeywordRecognizer matches "Hey 49", then a time-of-day greeting. It's the one Azure piece the local build kept. It matches against keyword.table on disk, so nothing leaves the machine. You can talk over the greeting.
02
OPEN THE SESSION Cloud: a WebSocket to the Gemini Live API. 16 kHz mono PCM goes up while you're still talking. Local: NAudio captures with silence detection and POSTs the WAV to faster-whisper, a turn at a time. The cloud build is genuinely speech-to-speech: there's no transcript in the middle. If the socket faults or the key's bad, it drops back to the old turn-based Azure path for one conversation and says so out loud, then retries Live on the next wake word.
03
ROUTE The whole tool catalogue goes up as schemas, alongside recent turns. What comes back is a batch of tool calls, a sequence it built out of primitives, or just an answer. Search is grounded in-session on the cloud build; on the local one it's another tool, so it only fires when the model decides it needs one.
04
DISPATCH Each tool is validated against its schema, then run in order. Compound requests show up as several calls at once. If one fails validation the rest still run. If the LLM times out or hands back junk, there's a keyword matcher behind it, and plain chat behind that.
05
SPEAK The reply plays as it arrives (the model's own voice on cloud, Kokoro on local) with the glass bubble alongside it. Say "Hey 49" to cut it off. A second wake-word listener runs the whole time it's talking. When that one fires, playback stops mid-word and the bubble slides away.

What it can do

[ 38 tools · 9 domains ]

Every capability gets registered once, with an LLM-facing schema and a keyword predicate for the fallback path. Here's what's in there right now.

Standing rules & suggestions [ 05 ]

"tell me when my download finishes" A rule it keeps and acts on by itself
"every weekday at 8, turn on the light" Same thing, recurring
"what rules do I have?" Read them back, cancel any of them
"stop suggesting things" It offers things unprompted; this turns that down

The rest of this layer has no tools behind it. It announces each prayer before it arrives, calculated locally, and it won't speak to an empty desk, in the middle of the night, or over a conversation you're already having. A reboot doesn't lose anything either. A plain timer pauses and comes back with the time that was left, an alarm keeps its moment, and whatever came due while it was off gets said in one sentence once I'm actually at the desk.

Call screening [ 03 ]

"screen my calls" Arms it for a while. The arm expires on its own
"hang up" Ends whatever call is live
"who called?" Reads back who rang and what they wanted

While it's armed, an incoming call gets answered through Phone Link. It greets whoever's calling, has a conversation, writes down a message and hangs up. It never picks up unless I've armed it first, and the arm times out on its own. I built it that way on purpose. The person on the other end is a stranger, so a call gets its own set of four tools and none of the other 38: a caller who asks it to send a text or turn on the lights gets nothing at all. It answers in the assistant's own voice and says so.

Composition primitives [ 02 ]

wait Pause N seconds. Only the LLM ever uses it
repeat Loop a sequence of tool calls N times

These two are here so the model can build things I never wrote a tool for. I never wrote a "flash the light" tool, but "flash my bedroom light 3 times" still works out to repeat(3, [on, wait 1s, off, wait 1s]). Neither one goes into conversation memory. There's no point remembering that it waited a second.

LLM-first dispatch

[ ARCHITECTURE ]

This used to be a hardcoded if / else if chain, and adding anything to it was miserable. Now one set of tool definitions feeds both the AI router and the offline fallback, and the dispatcher doesn't care whether it's talking to Gemini or a local OpenAI-compatible endpoint.

registry

One definition, two consumers

Each capability is a single VoiceCommand object carrying an LLM-facing schema (name, description, typed params with enums) and a keyword predicate. The AI router reads the schema, the fallback matcher reads the predicate, and I only have to write the thing once.

multi-tool

Several tools per utterance

The model can return a batch of tool calls in one response. The dispatcher checks the args on each and runs them in order. A bad call gets dropped and the rest still go through.

planning

Building what isn't there

When no single tool fits, the router works out a sequence that does. control_lights + wait + repeat gets you a flashing light.

memory

Rolling conversation window

Recent turns get fed back so follow-ups like "turn it back off" resolve. Past tool calls are stored in each provider's native function-calling format. I found that one out the hard way: show a small model plain-text transcripts of its own tool calls and it starts writing very convincing fake ones as prose.

barge-in

Interrupt mid-reply

The whole point is never having to sit through an answer you didn't want. Say "Hey 49" over the top of a reply and it dies where it stands, then it's listening again.

IntentDispatcher.cs C# 
// Ask the LLM what to do, with the whole tool catalogue + recent history.
var decision = await detector(userInput, registry.ToolDefinitions, history)
               ?? LlmDecision.Failure();

if (decision.Failed)                // timeout / malformed JSON
    return await FallbackAsync(userInput, lower, history);  // keyword matcher

if (decision.IsToolCall) {          // one or more tools, in order
    foreach (var call in decision.ToolCalls) {
        var command = registry.FindByName(call.Name);
        if (command == null || !TryValidate(command.Tool, call.Arguments, out var args))
            continue;                   // bad call? drop it and keep going
        await command.Handler(context, args);
    }
    return false;
}

// Nothing to call, so just talk back. Still interruptible.
return await ConversationalAsync(userInput, history);

The speech bubble

[ PYTHON · PYGAME · VIA PYTHONNET ]

A frameless translucent panel that slides up from the bottom of the screen, shows what you said and what it's saying back, then slides away when it's done. Written in Python with pygame and PIL, called from C# over a live pythonnet bridge.

  • It's per-monitor DPI-aware and supersampled, so the rounded corners don't come out jagged.
  • Text draws in Segoe UI, but emoji runs get segmented out and rendered with Windows' color emoji font (seguiemj.ttf) through Pillow's embedded_color. They end up on the same line as everything else.
  • The voice and the bubble get different copies of the same reply. Emoji are stripped before the text reaches TTS, since there's nothing there to pronounce.

Two builds

[ CLOUD + LOCAL ]

The two branches share almost everything and swap out the AI backend. local-laith exists so the whole thing runs on my machine: no cloud, no per-query cost. The tradeoff is a weaker model doing the reasoning. Everything sits behind a shared interface, which is the only reason keeping the two branches in parity isn't a nightmare.

Computer control

[ EXPERIMENTAL BRANCH ]

On a separate branch it takes a screenshot, works out what's on screen with a vision model, then clicks and types to drive the computer itself. Handing an LLM my mouse needed guardrails, so there's a global kill-switch hotkey, exclusion zones it isn't allowed to click in, a spoken yes/no before every action, and an append-only log of what it did with screenshot hashes attached.
