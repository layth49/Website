Minecraft AI

An iron pickaxe, from nothing, on 6 GB of VRAM.

A language model that plays Minecraft by writing commands to itself. Give it an empty inventory and fifteen minutes, and a 1.8-billion-parameter model running on a laptop GPU gathers wood, mines ore, builds and fuels a furnace, and walks away holding an iron pickaxe.

What it actually does

The model never touches the game. It writes text, and something else does the touching.

01
The model types a command Given what it can see, it writes an ordinary line of text into its own output: !collectBlocks("oak_log", 4). That is the entire action space. No pixels, no keyboard, no controller. The model's only motor skill is choosing which string to emit next, which is why a benchmark here measures planning rather than reflexes.
02
The framework parses it and moves the body mindcraft-ce matches the string to a skill and drives Mineflayer, a protocol-level client. Pathfinding, digging and inventory handling all happen down here. Most of this project's bugs lived in this layer too, not in the model.
03
Nothing is modded into the game The bot reconstructs the world from network packets, the same ones your own game client receives. The server cannot tell it apart from a person, so it joins an ordinary survival world with friends already in it. It runs on a Fabric 1.21.6 server behind a playit.gg tunnel, with a custom skin and optional local text-to-speech.

The ladder

Six crafting tasks, each a longer chain than the last, three trials each on a fixed clock. The top rung is the one that matters. iron_from_nothing starts with an empty inventory and 900 seconds, and the bot has to run the whole chain unaided: gather wood, craft a bench and wooden tools, mine stone, find iron, gather cobblestone, build a furnace, pick a fuel, smelt, craft. It solved that three times out of three, in 115, 125 and 123 commands. That rung had been 0/2 for every model on every earlier benchmark here. The two hardest rungs together now sit at 5/6.

The most interesting failure on this ladder was not a model failure at all.

0/3 → 2/3

CRAFTING_STONE_PICKAXE

Nothing changed but the clock. The rung had been given the same 180 seconds as the wooden pickaxe, despite having to finish the entire wooden-pickaxe chain and then mine stone and craft again.

The solve times settle it. Once the budget went to 360 seconds, the two passes finished at 169.9 s and 181.9 s, both landing right at the old cap. The wooden rung's own passes had already been using 71 to 96 % of their budget, so there was never headroom for a second stage. The rung was not failing. It was being cut off.

Static benchmarks lie

There are two ways to score a model here, and they disagree about which one is best.

Scored on paper First place

Feed the model fixed situations and grade the command it writes. The local 1.8B model wins outright, and it is not close.

83 % intent · 97 % parseable · 0 % hallucinated · 155 ms

Scored in the world Second place

Put the same model on the ladder and see whether it actually comes back holding the pickaxe. It gets beaten.

the ladder, three trials a rung

Static measures whether a model emits a well-formed command. The ladder measures whether it can get the item. Those turn out to be different skills, and only one of them is the product.

The sharpest evidence is the router. The plan was to send fresh player messages to one model and mid-task continuations to the other, combining their measured strengths. On the static tier it looked excellent. In-game it scored 2/10, worse than either model alone, losing a rung both models pass individually and failing by looping !searchForBlock eleven times where either one solo finishes in six commands. Swapping models mid-task destroys plan continuity: each inherits a history the other wrote and re-decides instead of continuing. The static tier structurally could not see this, because each of its cases is one handoff into a pre-written history, while a real task is roughly twenty handoffs, each depending on a plan the model formed itself. A stickier second version fixed both diagnosed defects, cut hallucinated commands from 60 % to 29 %, and scored 1/10. The premise was wrong rather than the heuristic. That file is kept, annotated with both results, and marked do-not-use.

The bugs underneath

Roughly 25 of them, and the worst never printed an error.

These came out of running off the maintained path: a bot without operator permissions, a spruce taiga instead of an oak forest, models under a billion parameters, many runs back to back. None are architectural flaws. They are unmaintained-surface bugs, code that works on the path the maintainers exercise and degrades quietly off it. The severe class is not small errors. It is silent failures that log success.

src/agent/tasks/tasks.js the worst one 
await this.agent.bot.chat(`/clear ${this.name}`);
console.log(`Cleared ${this.name}'s inventory.`);   // prints either way

Clearing the inventory between trials needs operator permission, which a correctly configured bot does not have, and the code logged success whether or not the command worked. So the world kept the bot's inventory between runs, and the validator saw the target item already sitting there at spawn and reported the task solved before the model had acted. A 0.87B model “cleared” an iron pickaxe instantly. Nothing crashed. It produced a clean 10/10 results table that was entirely fiction, and the only tell was the command count: real runs issue commands after the opening goal, and these issued exactly one.

  • Collection counted digs, not items. The counter incremented when the dig succeeded, not when the item reached the inventory, so the bot would log a collected log and then fail the very next craft for want of it. Of 41 collection events followed by an inventory dump, 29 (71 %) show the item absent.
  • Wood-variant handling existed and was unreachable. The logic for every wood type was written and correct, and was called from exactly one module that the agent path never touches. Built, shipped, stranded. That is a different failure mode from nobody having thought of it.
  • A hardcoded oak preference. Recipe candidates were sorted to prefer oak_planks, so in a spruce taiga the bot got told it needed a wood the biome does not have, and went hunting for it.
  • Deepslate iron was never searched for. The variant expansion appended the deepslate prefix only to names already ending in “ore”, so below y=0, where deepslate is most of the stone, the iron rung was looking for ore that does not spawn there. On the rung nothing had ever cleared.
  • Two sibling commands contradicted each other. One accepts a search range down to 10 and quietly clamps it up to 32; its sibling declares a minimum of 32 and hard-rejects the same value. Six rejections in one scenario. A model cannot learn one rule from two contradictory ones.

You cannot tell it anything

The most useful thing this project taught me is not about Minecraft. A small fine-tuned model does not reliably act on instructions that arrive in its result text. Not warnings, not corrections, not even a plan it wrote itself. Three independent confirmations landed in a single overnight run.

224 ignored warnings

A blocked command kept being emitted. 224 consecutive refusals changed nothing about what it did next.

292 identical hallucinations

One trial made 296 model calls and executed 6 commands, emitting the same deleted command 292 times. It is fine-tuned on this framework, so it emits what it remembers, not what it is shown.

1 smelt, when it needed three

A trial finished one smelt from success holding 7 raw iron and a furnace, with SMELTING REQUIRED printed verbatim in its own plan.

Better wording is not a lever. The only lever is removing the need to decide. So the framework absorbed the decisions. Crafting now makes its own intermediates and smelts them, places its own workbench, builds its own furnace when it holds the stone, and picks its own fuel. That is a real change to what the benchmark measures, turning the task into “can it gather the materials” rather than “can it plan the smelt”, and it was made deliberately, on the evidence that this model cannot be told.

What all that work bought

Fourteen framework fixes in one night. Two numbers moved enormously. The one that mattered did not move at all.

Turn efficiency 9 % → 97 % Commands actually executed per model call. Most of a trial had been going nowhere.
Hallucinations per trial 292 → 1 The single biggest efficiency change of the night.
Success on the hardest rung unchanged Nine of eighteen across the night. Exactly 50 %, start to finish, through all fourteen fixes.

Worth stating plainly rather than burying: the framework work bought robustness and speed, not capability. It made the agent much healthier without making it any smarter. What did raise capability was the other thing entirely, taking decisions away from the model and putting them in code that always makes them correctly.

What it still cannot do

Every number on this page comes from self-prompted task mode, with the bot given a goal and left alone. That is a narrow slice of what “an AI that plays Minecraft” could mean, so here is exactly where the measurements stop. This is scope, not a roadmap. None of it is promised.

The measurement was the hard part

A benchmark reported 10/10 for a model that had not taken a single action, and the only tell was a command count. Most of this project was learning to trust its own numbers. The payoff was a 1.8-billion-parameter model on a 6 GB card walking out of an empty world holding an iron pickaxe.
