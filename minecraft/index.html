Minecraft AI

An iron pickaxe, from nothing, on 6 GB of VRAM.

A language model that plays Minecraft by writing commands to itself. Nothing is modded into the game — the bot is an outside client reading the same network packets your own game reads, and every move it makes starts as a line of text the model chose to type. Drop it into an empty world with an empty inventory and a fifteen-minute clock, and a 1.8-billion-parameter model running on a laptop GPU gathers wood, builds tools, mines ore, builds and fuels a furnace, and walks away holding an iron pickaxe. Three runs out of three.

What it actually does

The model never touches the game. It writes text, and something else does the touching.

The bot is called LAITH49. It runs on mindcraft-ce against a Minecraft Java 1.21.6 server, and the whole mechanism is worth being precise about, because it isn't what people usually picture when they hear "AI plays Minecraft."

step one

The model types a command

Given what it can see, the model writes an ordinary line of text into its own output: !collectBlocks("oak_log", 4). That's the entire action space. No pixels, no keyboard, no controller — the model's only motor skill is choosing which string to emit next.

step two

The framework parses it and moves the body

mindcraft-ce reads that string, matches it to a skill, and drives Mineflayer, a protocol-level Minecraft client. Pathfinding, digging and inventory handling all happen down here, not in the model.

step three

Nothing is modded into the game

The bot is an external client reconstructing the world from network packets — the same packets your game client receives when you play. The server has no idea it isn't a person. That's also why it can join a normal survival world with friends in it.

the constraint

Six gigabytes of VRAM

One RTX 4050. Every local-model decision on this project falls out of that number: the daily driver is a 1.8B fine-tune because that is what fits alongside a running game server. When you read "a small model did this," the smallness is the point.

The ladder

Six crafting tasks, each one a longer chain than the last.

Scoring an agent like this is the hard part, so the benchmark is a ladder: six tasks of increasing depth, three trials each, on a fixed clock. The top rung, iron_from_nothing, is the one that matters — empty inventory, 900 seconds, and the bot has to run the entire chain unaided: gather wood, craft a bench and wooden tools, mine stone, find iron, gather cobblestone, build a furnace, pick a fuel, smelt, craft. It solved that three times out of three, in 115, 125 and 123 commands. It had been 0/2 for every model on every earlier benchmark here.

The two hardest rungs together sit at 5/6 on current code. The interesting failure on this ladder, though, wasn't a model failure at all.

the rung that wasn't failing

crafting_stone_pickaxe went 0/3 to 2/3 with no change but the clock

It had been given the same 180 seconds as the wooden pickaxe, despite having to finish the entire wooden-pickaxe chain and then mine stone and craft again. The wooden rung's own three successes used 71–96% of that budget, so there was no headroom left for a second stage. Raised to 360 s, it passed twice — and the solve times settle it: 169.9 s and 181.8 s, both landing right at the old cap. The rung was never failing. It was being cut off.

Which model drives it

Slower per decision, and finished sooner.

Same framework, same fixes, same rung (crafting_iron_pickaxe) — only the model swapped. The local 1.8B model is competitive on whether it eventually gets there. It is not competitive on how long it takes to decide what to do.

Static benchmarks lie

The model that wins on paper comes second in the world.

There are two ways to score a model here. Feed it fixed situations and grade the command it writes — the local 1.8B model wins that, at 83% intent, 97% parseable, 0% hallucinated commands, 155 ms. Or put it on the ladder and see whether it actually gets the item — where it comes second. Static measures whether a model emits a well-formed command. The ladder measures whether it can get the pickaxe. Those turn out to be different skills, and only one of them is the product.

the router

Combining the two models scored worse than either one alone

The plan was to send fresh player messages to one model and mid-task continuations to the other, combining their measured strengths. On the static tier it looked excellent. In-game it scored 2/10 — it lost a rung both models pass individually, and failed by looping !searchForBlock eleven times where either model solo finishes in six commands.

why

Swapping models mid-task destroys plan continuity

Each model inherits a history the other one wrote, and re-decides instead of continuing. The static tier structurally could not see this: each of its cases is one handoff into a pre-written history, while a real task is roughly twenty handoffs, each depending on a plan the model formed itself.

and fixing it didn't help

A stickier version fixed both defects and got worse

Hallucinated commands fell from 60% to 29%. Task success dropped to 1/10. The premise was wrong rather than the heuristic: once routing is sticky enough to preserve a plan, a task run is essentially all one model anyway, with every switch a fresh chance to break something. The file is kept, annotated with both results, and marked do-not-use.

The bugs underneath

Roughly 25 of them, and the worst ones never printed an error.

All of these came out of running off the maintained path — a bot without operator permissions, a spruce taiga instead of an oak forest, models under a billion parameters, many runs back to back. None of them are architectural flaws. They are unmaintained-surface bugs: code that works on the path the maintainers exercise and degrades quietly off it. And the severe class isn't small errors. It's silent failures that log success.

src/agent/tasks/tasks.js the worst one 
await this.agent.bot.chat(`/clear ${this.name}`);
console.log(`Cleared ${this.name}'s inventory.`);   // prints either way
a benchmark that scored a model that never moved

A clean 10/10 results table that was entirely fiction

Clearing the inventory between trials needs operator permission, which a correctly-configured bot doesn't have — and the code logged success whether or not the command worked. So the world kept the bot's inventory between runs, and the validator saw the target item already sitting there at spawn and reported task successful before the model had acted. A 0.87B model "cleared" an iron pickaxe instantly. Nothing crashed. The only tell was the command count: real runs issue commands after the opening goal, and these issued exactly one.

phantom collection

collectBlock counted digs, not items

The counter incremented when the dig succeeded, not when the item reached the inventory. So the bot would log "Collected 1 oak_log", and the very next command — nothing in between — would fail with you do not have the resources. Measured: of 41 collection events followed by an inventory dump, 29 (71%) show the item absent. It now reports the actual inventory delta.

written, working, unreachable

Wood-variant handling nothing could call

The logic for handling every wood type existed and was correct. It was used from exactly one module — a subsystem the agent path never calls. The capability was built, shipped and stranded. That's a different failure mode from nobody having thought of it.

a hardcoded preference

Told to find oak, in a forest with no oak

Recipe candidates were sorted to prefer oak_planks. In a spruce taiga the bot holds spruce, but the chosen recipe — and the error message built from it — names oak. So the bot gets told it needs a wood the biome does not have, and goes hunting for it. Recipe ranking is inventory-aware now, and wood ingredients are named generically.

on the rung nothing had cleared

Deepslate iron was never searched for

The ore-variant expansion added iron_ore for "iron", then appended the deepslate prefix only to names already ending in "ore" — so the deepslate variant was never added. Below y=0, where deepslate is most of the stone, the iron rung was searching for ore that doesn't spawn there.

two rules for one parameter

Sibling commands that contradicted each other

!searchForBlock accepts a search range down to 10 and quietly clamps anything under 32 upward. !searchForEntity declares a minimum of 32 and hard-rejects the same value. Same parameter, same concept, opposite behaviour — six rejections in a single scenario. A model cannot learn one rule from two contradictory ones.

You cannot tell it anything

Three confirmations in one night, and the fix was to stop asking.

The most useful thing this project taught me is not about Minecraft. A small fine-tuned model does not reliably act on instructions that arrive in its result text — not warnings, not corrections, not even a plan it wrote itself. Three independent confirmations landed in a single overnight run.

224 times

It ignored every blocked-command warning

A blocked command kept being emitted. 224 consecutive blocked messages changed nothing about what it did next.

292 times

It kept calling a command that no longer existed

One trial made 296 model calls and executed 6 commands: it emitted the same non-existent command 292 times, one that had been removed from its documentation entirely. The model is fine-tuned on this framework, so it emits what it remembers, not what it's shown. Removing a command from the docs doesn't remove it from the model — it just makes the failure silent.

its own plan

It finished one smelt away from success, holding the instructions

Seven raw iron, a furnace, a wooden pickaxe and four sticks in hand; it needed three ingots. Its own planning tool had already printed "SMELTING REQUIRED — these cannot be crafted, they must be smelted in a furnace." It called the smelt command once in the entire trial.

Better wording is not a lever. The only lever is removing the need to decide. So the framework absorbed the decisions: crafting now makes its own intermediates and smelts them, places its own workbench, builds its own furnace when it has the stone, and picks its own fuel. That is a real change to what the benchmark measures — the task becomes "can it gather the materials" rather than "can it plan the smelt" — and it was made deliberately, on the evidence that this model cannot be told.

What all that work actually bought

Two numbers moved enormously. The one that mattered didn't move at all.

Fourteen framework fixes landed in one night. The agent got dramatically healthier by every process measure available. Here is what that did to the thing the whole exercise was for:

Turn efficiency 9% → 97%

Commands actually executed per model call. Most of a trial had been going nowhere.

Hallucinations 292 → 1

Per trial. The single biggest efficiency change of the night.

Success, hardest rung unchanged

Nine of eighteen across the night. Exactly 50%, start to finish, through all fourteen fixes.

That is worth stating plainly rather than burying: the framework work bought robustness and speed, not capability. It made the agent much healthier without making it any smarter. What did raise capability was the other thing entirely — taking decisions away from the model and putting them in code that always makes them correctly.

What it still can't do

Scope, not a roadmap. None of this is promised.

Every number on this page comes from self-prompted task mode — the bot given a goal and left alone. That's a narrow slice of what "an AI that plays Minecraft" could mean, and it's worth being exact about where the measurements stop.

  • Conversation is unmeasured. Nobody has checked whether it answers a question well, follows a chat request, or remembers the previous turn. It can talk. Whether it's any good to talk to is not something this project measured.
  • No multi-agent work. One bot, alone.
  • The Nether and portals: zero coverage.
  • No code generation. The framework can have the model write new actions as code; that path was never exercised here.
  • No vision. The bot reads world state from packets, never from pixels.
  • The three cloud models tied at 3/3. That rung is saturated, so which of them is actually best here is unresolved — separating them needs a harder task or more trials.
Removing decisions beat improving prompts

The measurement was the hard part

A benchmark reported 10/10 for a model that had not taken a single action, and the only tell was a command count. Most of this project was learning to trust its own numbers — and the payoff was a 1.8-billion-parameter model on a 6 GB card walking out of an empty world with an iron pickaxe.
